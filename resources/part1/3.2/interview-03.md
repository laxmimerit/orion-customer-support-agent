# Fictional customer interview 3

Role: SaaS founder

This is authored teaching material, not an actual customer interview. The participant is evaluating a possible trial; no purchase or product result is established.

Participant: I still answer tickets between product work and sales calls, so administration has a real opportunity cost.

Interviewer: Walk me through the first hour of your support day.

Participant: I begin with unresolved conversations from yesterday, then check new messages before the stand-up. The inbox shows arrival order, but it does not show which customer is waiting for an internal decision. I keep a separate list of promises made in replies. That list is useful, although updating it takes time and occasionally two people maintain different versions. We can run a small pilot, but we cannot fund a lengthy integration project.

Interviewer: How do you assign a ticket when its owner is away?

Participant: We post in the team channel and ask someone to take over. A name on the ticket is helpful only if that person is actually available. The replacement needs the previous promise, the customer’s latest question and the next action. I would like a visible handoff acknowledgement. Simply changing the owner without telling either person would make the problem worse. I would rather start with one useful workflow than configure every possible feature.

Interviewer: What happens when a customer sends the same issue twice?

Participant: The second message often contains a useful screenshot or a clearer explanation, so I would not delete it as a duplicate. I want to see the relationship and retain both original messages. Two agents sometimes draft separate answers, which confuses the customer. A suggested match would save investigation time, but a person should confirm that the cases really match. Make the costs visible before asking me to enter payment details.

Interviewer: How do you review a proposed reply?

Participant: I compare the proposed answer with the customer’s request and the evidence in the conversation. Names, dates, amounts and promised actions need particular attention. A polished sentence can still contain an invented commitment. I would accept a draft with clear source links and an edit history. Automatic sending would be a separate decision, and I would not enable it during the trial. We can run a small pilot, but we cannot fund a lengthy integration project.

Interviewer: Which service measure do you trust today?

Participant: We can count tickets reasonably well, but I distrust our average response time. Unanswered messages sometimes disappear from the report, and other exports treat them as zero. Both approaches change the story. I want the count of observed responses alongside the median, plus the number still waiting. A date filter also needs to explain whether it means creation or resolution date. I would rather start with one useful workflow than configure every possible feature.

Interviewer: Tell me about a recent handoff that went wrong.

Participant: A customer asked about a change to their invoice. The morning shift checked the seat history and left an internal note, but the next shift saw only the latest email. They asked for the same information again. The customer was understandably annoyed. We resolved it eventually, but the delay came from missing context rather than a difficult billing calculation. Make the costs visible before asking me to enter payment details.

Interviewer: How do you explain subscription costs internally?

Participant: I need a monthly total I can explain before asking for approval. A low per-seat price is less useful if there is a minimum number of seats, a required annual contract or a separate charge for archived tickets. Please show what happens when we add two reviewers. I would also separate software fees from model usage instead of calling everything unlimited. We can run a small pilot, but we cannot fund a lengthy integration project.

Interviewer: What information would you allow an AI tool to use?

Participant: We could use a small set of redacted tickets initially. Passwords, access tokens and unrelated customer records should never be included. The person reviewing a draft must only see information they are authorised to access. I also need to know where data is sent and how to remove it after the trial. Those answers matter more than a broad claim about security. I would rather start with one useful workflow than configure every possible feature.

Interviewer: How would you test an export before relying on it?

Participant: I would choose a known date range and compare record counts with the source queue. Then I would check a ticket with several messages, one with no response and one reopened case. I would inspect timestamps and encoding as well as the totals. A file that opens successfully can still be incomplete. Repeating the export should give the same snapshot or explain why it changed. Make the costs visible before asking me to enter payment details.

Interviewer: What would make you stop a beta trial?

Participant: I would pause if the system confidently mixed up two customers, sent something without review or made it impossible to recover the original record. Smaller mistakes could be learning opportunities if we can see and correct them. The trial needs a clear reporting route and an owner for each problem. I do not expect perfection, but I do expect understandable behaviour. We can run a small pilot, but we cannot fund a lengthy integration project.

Interviewer: Who makes the final purchase decision?

Participant: The support team would assess usefulness, engineering would check integration and someone responsible for spending would approve the purchase. Those are different questions. A convincing demonstration alone does not settle all three. We would need a written scope, a realistic estimate and an exit path. I would prefer a narrow trial that produces evidence each reviewer can inspect. I would rather start with one useful workflow than configure every possible feature.

Interviewer: What would you want to see in a two-week pilot?

Participant: I would select a small set of ordinary cases and a few difficult ones before starting. We would record draft edits, classification mistakes, missing context and time spent reviewing. At the end, we could compare those notes with our existing workflow. I would not claim a percentage improvement from a handful of examples. The first goal is to learn whether the workflow is dependable. Make the costs visible before asking me to enter payment details.
